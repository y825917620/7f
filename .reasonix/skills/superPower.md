# Superpowers 工作流

这是基于 obra/superpowers 的完整 Agent 开发方法论。当用户提出一个开发任务时，按以下流程执行。

---

## 阶段 1：需求澄清 (Brainstorming)

**在写任何代码之前，必须先做这个阶段。**

### 检查清单

1. **探索项目上下文** — 查看文件、文档、最近的提交
2. **逐一提问** — 一次只问一个问题，理解：目的、约束、成功标准
3. **提出 2-3 种方案** — 说明各自的权衡，给出你的推荐
4. **分块呈现设计** — 按复杂度拆分，每块征得用户确认
5. **保存设计文档** — 写入 `docs/superpowers/specs/YYYY-MM-DD-<主题>-design.md`

### 核心原则

- **一次只问一个问题** — 不要用多个问题轰炸用户
- **首选选择题** — 比开放题更容易回答
- **YAGNI 无情** — 从设计中移除所有不必要的功能
- **探索替代方案** — 在确定方案前总是提出 2-3 种做法
- **增量验证** — 呈现设计，获得批准后再继续

### 红线（禁止行为）

| 想法 | 真相 |
|------|------|
| "这只是一个简单问题" | 问题就是任务。先走流程。 |
| "我需要更多上下文" | 技能检查先于澄清问题。 |
| "这个不需要正式设计" | 每个项目都需要设计，再简单也一样。 |
| "我先快速做这一件事" | 在做任何事之前先检查。 |

---

## 阶段 2：编写计划 (Writing Plans)

设计方案获批准后，编写详细的实施计划。

### 计划格式

```markdown
# [功能名称] 实施计划

**目标：** [一句话描述]

**架构：** [2-3 句描述方法]

**技术栈：** [关键技术/库]

---

### 任务 N：[组件名称]

**文件：**
- 创建：`src/path/to/file.py`
- 修改：`src/path/to/existing.py`
- 测试：`tests/path/to/test.py`

- [ ] **步骤 1：编写失败测试** — 具体代码
- [ ] **步骤 2：运行测试确认失败** — 具体命令 + 预期输出
- [ ] **步骤 3：编写最小实现** — 具体代码
- [ ] **步骤 4：运行测试确认通过** — 具体命令 + 预期输出
- [ ] **步骤 5：提交** — `git commit`
```

### 粒度规则

- **每个步骤是一个独立操作（2-5 分钟）**
- 每个步骤必须包含 **完整代码**，不能有占位符
- **精确文件路径**，不能模糊
- 精确的命令 + 预期输出

### 禁止的占位符

❌ "TBD", "TODO", "稍后实现"
❌ "添加适当的错误处理" — 必须写出具体处理逻辑
❌ "类似任务 N" — 代码要完整，不要交叉引用
❌ 未在任何任务中定义的类型、函数、方法引用

---

## 阶段 3：子代理开发 (Subagent-Driven Development)

选择以下两种方式之一执行计划：

### 选项 A：子代理驱动（推荐）

使用 `todo_write` 追踪任务进度，为每个任务：

1. **调用 `run_skill({ name: "explore", arguments: "..." })`** 让子代理在隔离上下文中阅读相关文件
2. **实施** — 读取、修改文件
3. **验证** — 运行测试确认通过
4. **代码审查** — 在任务间做简短的代码质量检查

### 选项 B：内联执行

在当前会话中直接按计划步骤执行，每个步骤完成后征得用户确认。

---

## 阶段 4：代码审查 (Code Review)

实施完成后做最终检查：

1. **对照计划** — 所有功能都实现了？
2. **测试覆盖** — 是否有未测试的路径？
3. **代码质量** — 命名、结构、错误处理是否合理？
4. **呈现选项** — 合并 / PR / 保留分支 / 丢弃

---

## 阶段 5：分支完成 (Finishing)

- 运行完整测试套件确认通过
- 提交并推送
- 询问用户：合并到主分支 / 创建 PR / 保留分支 / 丢弃
