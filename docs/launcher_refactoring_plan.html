神龙地图启动器底层地图资源接入规划

目标不是继续盲猜游戏如何加载地图，而是把底层加载链路研究清楚，形成启动器自己的地图资源接入层。 启动器应能识别、校验、解包、挂载、传参并验证地图资源，让地图包成为可控输入，而不是依赖硬编码副作用。

一、当前审查证据

P1正式启动代码仍把地图 ID 固定为 10002。

src/launcher/game_launcher.py 中 mid_val = 10002 被用于共享内存、命令行、匿名管道和命名管道。 UI 传入的 selected_map 没有参与底层启动链路。

P1正式启动代码固定复制 map/10002_dec.bin。

当前只是把一个预解包文件复制到 sl/map.map 与 core/sl/map.map，没有从所选地图资源构建运行态地图包。

P1游戏日志证明启动层和资源层没有真正接通。

本次日志显示 设置读取地图名[10002]、begin load map[10002]，随后 读取地图[10002]失败。 这说明游戏已经进入加载流程，但接收到的地图身份和运行态资源没有满足引擎要求。

P2构建脚本引用不存在的 src.core.sl_handler。

这暗示项目曾经想做资源处理层，但当前源码里没有沉淀成正式模块。后续应以明确模块补齐，而不是散落在启动函数里。

二、底层研究发现

2.1 地图资源文件分层

文件类型 观察结果 规划含义
data/map/{id}.map 二进制头部样本以 54 e9 0b 00 ... 开始，体积通常小于解包后的运行包。 更像地图元数据、展示信息、选项、缩略图等来源，应由启动器解析并用于 UI 与配置生成。
data/map/{id}.sl 样本均可被 LZMA 解压，压缩头类似 5d 00 00 40 00 ...。 应作为运行态地图包主来源，由启动器解包并挂载给游戏。
解压后的地图包 样本统一以 LuaRDGTM 开头，10002_dec.bin 也是此类内容。 现有 10002_dec.bin 只是某一张图的已解包缓存，不应作为全局固定资源。
sl/map.map / core/sl/map.map 当前两处都被写入同一份解包内容。 这是一个候选挂载点，但需要通过游戏参数、日志和文件访问观察确认优先级。

2.2 游戏层可见入口

从 game.exe、gpigame.dll、核心脚本包和日志中可见以下关键字：

  • 命令行相关：/mapfile=、/livemapfile=、/pipe=、/livepipe=。
  • 内存映射相关：MemoryMapName=、默认名 sanguo。
  • 地图状态接口：SetLoadMap、UpdateMapID、IsMapOK、GetGameCheckSum、GetCheckSumData。
  • 日志阶段：GameInit、do [core/gpi.o] ok!、读取地图表格、begin load map、map is not ok。

结论：游戏可能支持不止一种地图输入方式。当前规划必须同时研究“文件挂载”“命令行指定”“共享内存/内存映射”“Lua 初始化接口”四条路径， 找到引擎真正认定地图有效的最小合同。

三、目标架构

将启动器改造成拥有独立地图资源接入层的结构，而不是把资源处理塞进 launch_game。

UI 选择地图 -> MapCatalog 读取 .map 元数据、名称、选项、缩略图 -> MapPackageAnalyzer 识别 .sl 压缩格式、解包、校验 LuaRDGTM 运行包 -> MapLaunchManifest 生成一次启动所需的统一清单 -> ResourceMountManager 按证据选择挂载策略：文件 / 命令行 / 内存映射 -> GameBridge 统一写入命令行、共享内存、管道、环境变量 -> LogVerifier 读取新日志，确认地图 ID、地图包和加载状态一致

核心模块规划

模块 职责 禁止事项
MapCatalog 扫描 data/map，建立地图 ID 到 .map/.sl 的索引，标记缺失、重复、异常大小。 不启动游戏，不修改资源。
MapPackageAnalyzer 只读分析 .sl，验证 LZMA、解包头、解包大小、哈希、是否包含预期脚本/资源段。 不根据单张 10002 推断所有地图。
MapLaunchManifest 为一次启动生成结构化清单：地图 ID、源文件、解包文件、挂载点、校验值、选项、玩家数。 不保存 UI 状态，不直接调用 Win32。
ResourceMountManager 按研究结果执行挂载：写入 sl/map.map，必要时尝试 /mapfile= 或内存映射 sanguo。 不硬编码 10002，不吞掉错误。
GameBridge 统一向游戏注入地图 ID：命令行、共享内存、匿名管道、命名管道必须来自同一份 manifest。 不自行选择地图，不读取 UI 控件。
LogVerifier 启动后解析最新日志，确认 设置读取地图名、begin load map、错误信息和 manifest 一致。 不把“启动进程成功”误判为“地图加载成功”。

四、游戏资源与地图资源完全可控化

本阶段目标是把启动器从“调用游戏”升级为“资源控制平台”。游戏引擎、公共资源、地图资源、编辑缓存、运行态挂载包必须彻底分层， 后续才能安全修改游戏内资源、直接编辑地图资源，并把修改后的资源重新接入启动流程。

4.1 资源分层模型

层级 建议目录 职责 是否允许编辑
游戏引擎层 game_runtime/core game.exe、gpigame.dll、基础 DLL、核心运行文件。 默认只读。除非明确进入引擎补丁模式。
公共游戏资源层 game_assets/base resource/sanguo、公共模型、贴图、图标、音效、字体等。 允许通过资源编辑器创建覆盖版本，不直接改原件。
原始地图库层 maps/source/{map_id} 保存原始 {map_id}.map、{map_id}.sl、原始哈希、来源信息。 只读。作为可恢复基线。
地图解包工作区 maps/workspace/{map_id} 解包后的 LuaRDGTM 内容、脚本、资源段、索引表、可编辑文件树。 允许编辑。所有修改先进入工作区。
覆盖补丁层 mods/{mod_id} 保存对公共资源或地图资源的覆盖文件、Lua patch、配置 patch。 允许编辑。支持启用/禁用。
运行态挂载层 cache/launch/{session_id} 一次启动生成的最终地图包、资源覆盖结果、manifest、日志快照。 自动生成，不手动编辑。

4.2 Resource Manifest 作为唯一真实来源

后续所有资源操作都必须围绕结构化清单，不再依赖散乱文件名和硬编码路径。

  • game_manifest.json：记录游戏运行时版本、核心文件哈希、公共资源根目录。
  • map_manifest.json：记录地图 ID、地图名、原始 .map/.sl、解包哈希、可编辑段列表。
  • mod_manifest.json：记录资源覆盖、脚本 patch、依赖地图、兼容游戏版本。
  • launch_manifest.json：记录一次启动最终使用的游戏版本、地图版本、mod 列表、挂载策略、校验值。

4.3 地图包解包、编辑、重打包链路

  1. Import：导入 {map_id}.map 与 {map_id}.sl，计算原始哈希，写入 source 层。
  2. Unpack：解压 .sl 得到 LuaRDGTM 运行包，解析段表、脚本名、资源名、偏移、大小。
  3. Normalize：将可识别段转换为工作区文件树，例如 Lua 脚本、模型引用、图标、配置表、地图描述。
  4. Edit：通过启动器编辑工作区内容，保留修改记录和 diff，不直接覆盖 source。
  5. Validate：检查 Lua 语法、资源引用、缺失文件、段大小、编码、路径大小写。
  6. Pack：从工作区重新生成 LuaRDGTM 运行包，并按游戏要求重新压缩为可挂载地图包。
  7. Mount：通过 manifest 把重打包结果接入启动流程。

4.4 公共游戏资源可编辑链路

  1. 扫描 resource/sanguo，建立模型、贴图、图标、音效、UI 素材索引。
  2. 为每个资源记录路径、大小、格式、哈希、被哪些地图或脚本引用。
  3. 编辑公共资源时不修改 base 原件，而是在 mods/{mod_id} 中创建覆盖文件。
  4. 启动前由 ResourceOverlayResolver 合成“base + mod + map override”的最终资源视图。
  5. 如果游戏只支持物理目录读取，则运行态挂载层负责生成临时覆盖目录或临时替换，并在 manifest 中记录。

4.5 资源编辑器能力规划

编辑对象 一期能力 后续能力
Lua 脚本 查看、搜索、语法校验、只读引用跳转。 安全编辑、diff、回滚、重打包。
地图选项 解析 #T# 选项、默认值、玩家数。 可视化编辑选项并重新写入地图包。
贴图/图标 预览 bmp/dds/tga，建立引用索引。 替换资源、格式转换、生成 mod 覆盖。
模型/动画 列出 apm/lmo/caf 文件和引用关系。 替换模型、检查缺失贴图、预览基础信息。
地图包整体 解包、哈希、结构浏览、挂载测试。 重打包、版本管理、发布导出。

4.6 可控资源的安全机制

  • 所有原始资源进入 source/base 后只读保存，任何编辑都走 workspace 或 mod。
  • 每次编辑生成版本记录，可回滚到任意历史版本。
  • 每次启动生成独立 launch_manifest.json，保证问题能追踪到具体资源版本。
  • 重打包前必须通过资源引用校验，避免游戏启动后才发现缺贴图、缺脚本、缺模型。
  • 支持“干运行”：只生成最终挂载包和校验报告，不启动游戏。

五、底层研究路线

阶段 A：建立事实基线

  1. 抽样至少 10 张地图，记录 .map 大小、.sl 大小、解包大小、头部、哈希和解包结果。
  2. 确认所有 .sl 是否都能 LZMA 解包；对失败样本单独分类，避免一个算法覆盖不了所有地图。
  3. 确认 LuaRDGTM 之后的结构：段数量、偏移表、内嵌脚本名、资源名、校验字段。
  4. 建立 docs/map_resource_format.md，只记录已证实字段，未知字段标记为 unknown，不猜含义。

阶段 B：定位游戏真实加载合同

  1. 整理 game.exe 支持的命令行参数，重点验证 /mapfile=、/livemapfile= 是否可替代 sl/map.map。
  2. 验证 MemoryMapName=sanguo 的含义：是地图包内存映射、直播/编辑器通道，还是兼容入口。
  3. 观察游戏启动时实际读取哪些文件：sl/map.map、core/sl/map.map、map/{id}.map、map/{id}.sl。
  4. 梳理 SetLoadMap、UpdateMapID、IsMapOK 在日志中的先后顺序，确认失败点位于“包读取”“校验”“Lua 初始化”哪一层。

阶段 C：设计可控挂载策略

  1. 文件挂载策略：启动器解包 {id}.sl 到受控缓存，再原子替换 sl/map.map 与必要的镜像路径。
  2. 参数挂载策略：如果 /mapfile= 被证实有效，则优先传入缓存文件绝对路径，减少覆盖游戏目录文件。
  3. 内存映射策略：如果 MemoryMapName=sanguo 被证实是地图包入口，再实现映射写入；未证实前不作为默认方案。
  4. 回滚策略：启动失败时保留 manifest 和日志，不静默恢复现场，便于定位。

阶段 D：把地图资源正式接入启动器

  1. UI 选择地图后，不再只传一个数字，而是生成 MapLaunchManifest。
  2. 启动按钮只在 manifest 校验通过后可用；资源缺失或解包失败直接在 UI 提示。
  3. 启动前输出本次 manifest 到 data/launcher_logs，包括地图 ID、源路径、解包路径、哈希、挂载策略。
  4. 游戏启动后由 LogVerifier 自动读取新日志，判断是否真正加载到所选地图。

六、实验矩阵

所有实验都应是可复现、可记录、可回滚的，不使用旧测试脚本作为依据。

实验 变量 观测项 通过标准
文件挂载验证 只替换 sl/map.map，地图 ID 与所选一致。 init.log 的地图名、begin load map、error.log。 日志地图 ID 与 manifest 一致，且不出现读取地图失败。
镜像路径验证 分别写入 sl/map.map、core/sl/map.map、两者同时写入。 游戏是否读取不同路径，失败信息是否变化。 确认最小必要挂载路径。
命令行 /mapfile= 验证 传入缓存地图包路径，不覆盖 sl/map.map。 日志是否显示对应文件或地图 ID，是否进入地图加载。 确认参数是否可作为正式挂载入口。
内存映射验证 创建 sanguo 映射并写入地图包，控制是否同时存在文件挂载。 日志、读取结果、是否需要文件 fallback。 只有证实有效才纳入默认策略。
校验链验证 比较不同地图解包哈希与 GetGameCheckSum / GetCheckSumData 相关日志。 校验失败是否导致 map is not ok 或读取失败。 明确 checksum 是否需要启动器预计算或传递。

七、编码实施计划

第 1 步：资源格式研究产物先落地

  • 新增 docs/map_resource_format.md：记录 .map、.sl、解包运行包的已知结构。
  • 新增 docs/game_launch_contract.md：记录游戏启动参数、共享内存名、管道数据结构、日志阶段。
  • 新增 docs/map_mounting_decisions.md：每个挂载策略的证据、结论和废弃原因。

第 2 步：实现只读索引与分析层

  • MapCatalog 扫描地图库，输出地图资源完整性状态。
  • MapPackageAnalyzer 只读解包并验证 LuaRDGTM 头，不写游戏目录。
  • 为异常地图生成诊断信息：缺 .sl、缺 .map、解包失败、头部异常、体积异常。

第 3 步：建立资源可控化工作区

  • 实现 maps/source、maps/workspace、mods、cache/launch 的目录规范。
  • 导入地图时自动生成 map_manifest.json，并保留原始资源哈希。
  • 解包地图时只写入 workspace，不污染游戏运行目录。
  • 为公共游戏资源建立只读 base 索引，并预留 mod 覆盖层。

第 4 步：实现 manifest 驱动的启动

  • 用 MapLaunchManifest 替代散乱参数传递。
  • manifest 作为唯一来源驱动：地图 ID、资源路径、解包路径、挂载策略、配置选项。
  • launch_game 不再自己判断地图资源，只消费 manifest。

第 5 步：接入挂载策略

  • 先实现已证实的文件挂载策略。
  • 再根据阶段 B 的证据决定是否加入 /mapfile= 策略。
  • 内存映射策略必须等证据充分后再实现，避免把未知机制变成新依赖。

第 6 步：启动链路统一注入

  • 命令行地图 ID、共享内存地图 ID、匿名管道地图 ID、命名管道地图 ID 全部来自 manifest。
  • 彻底移除 mid_val = 10002 和固定 10002_dec.bin。
  • 资源准备失败时不创建游戏进程。

第 7 步：日志闭环验证

  • 启动前记录 manifest。
  • 启动后解析最新 init.log、error.log、log_mgr。
  • UI 显示真实状态：进程已启动、地图加载中、地图加载成功、地图读取失败、Lua 初始化失败。

第 8 步：资源编辑与重打包能力

  • 先实现只读浏览和引用索引，再开放编辑。
  • 编辑能力必须先支持 diff、回滚、校验，再允许重打包。
  • 重打包结果必须通过独立 manifest 接入启动，不覆盖原始地图。

八、验收标准

  • 必须 任意选择 10002 之外的地图时，日志中的 设置读取地图名 与 UI 选择一致。
  • 必须 启动器能解释本次使用了哪个地图源文件、哪个解包文件、哪个挂载策略。
  • 必须 所有地图资源处理逻辑集中在资源接入层，不散落在 UI 或 Win32 启动代码里。
  • 必须 缺资源、解包失败、挂载失败、地图校验失败都有明确错误信息。
  • 必须 原始游戏资源和原始地图资源保持只读，所有修改都进入 workspace 或 mod 层。
  • 必须 启动器能生成并读取 game_manifest.json、map_manifest.json、launch_manifest.json。
  • 必须 至少一张地图可以完成“导入 -> 解包 -> 生成工作区 -> 重新挂载启动”的闭环。
  • 建议 至少一个公共资源覆盖 mod 可以被 manifest 挂载，并可随时禁用恢复原状。
  • 必须 至少 3 张不同体积地图完成启动验证，包括 10002 和两张非 10002。
  • 建议 至少 10 张地图完成离线解包与 manifest 生成验证。

九、边界与优先级

当前阶段只做本地地图资源接入和启动稳定性。联机、赞助/VIP、外部服务模拟、权限绕过等内容不进入本轮规划。 底层研究只服务于让本地已有地图资源被启动器正确、可控、可验证地加载。

  1. 最高优先级：资源分层、manifest、地图资源接入层、统一地图 ID、日志验证。
  2. 第二优先级：地图解包工作区、公共资源索引、mod 覆盖层。
  3. 第三优先级：配置生成与地图选项联动。
  4. 第四优先级：打包清理、UI 状态展示、错误诊断体验。
  5. 暂缓：联机、商业权限相关功能、界面大改。
